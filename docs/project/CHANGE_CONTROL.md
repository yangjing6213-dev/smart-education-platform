# 变更控制

## 1. 适用对象

任何影响阶段、范围、术语、三端职责、数据、权限、多租户、AI、安全、页面、流程、验收、提交或审查包的变化，都受本流程控制。

## 2. 变更级别

| 级别 | 示例 | 批准要求 |
|---|---|---|
| 文字澄清 | 不改变含义的错字或链接修正 | 任务合同授权，回执记录 |
| 基线解释 | 对既有合同作不删减的明确映射 | 项目负责人明确批准并写入决策基线 |
| 范围变更 | 新增、删除、弱化交付或改变阶段 | 当前合同下禁止；必须建立新版权威执行合同并重新批准 |
| 安全例外 | 涉及真实数据、密钥、跨租户、正式AI、支付、推送或部署 | 当前批次不接受；停止并转交项目负责人 |

## 3. 标准流程

1. **提出**：在任务合同中写明变更目标、原因、请求人和受影响文件；
2. **分析**：产品经理评估用户与范围影响，技术负责人评估架构、数据、工期和回滚影响；
3. **安全审查**：QA/安全智能体检查未成年人、隐私、租户、AI、密钥和证据风险；
4. **裁决**：项目负责人明确批准、拒绝或要求补证；沉默不视为批准；
5. **固化**：不删减解释可在当前合同下写入次级文件；范围、阶段、交付或冲突性变更必须先建立新版权威执行合同与新 SHA，再原子更新全部引用并重新批准；
6. **实施**：只修改批准白名单文件，禁止顺手重构或扩大范围；
7. **验证**：运行批准命令，检查差异并生成回执；
8. **停止**：提交证据，等待下一项单独授权。

## 4. 变更请求最小字段

- 变更编号与日期；
- 原基线与建议基线；
- 业务理由；
- 影响的 A0—A7 阶段、合同12项、文件和提交；
- 数据、租户、未成年人、AI、安全、成本和时间影响；
- 迁移或回退办法；
- 新验收点与验证命令；
- 项目负责人裁决与证据位置。

字段不完整时不得实施。

## 5. 当前合同的硬边界

指定 SHA 的当前合同下只允许不删减、不削弱、不扩张的解释。任何改变范围、阶段、交付，或与源合同冲突的变更，都必须：

1. 保持旧合同及其 SHA 冻结不变；
2. 创建有独立版本标识的新版权威执行合同并计算新 SHA；
3. 在同一原子变更中更新 `AGENTS.md`、决策基线、范围、计划、任务实例、模板和验证引用；
4. 由项目负责人重新批准新合同、全部引用和迁移边界；
5. 新批准完成前停止相关执行。

只修改决策基线、范围、计划或其他次级文件不能改变权威合同。

## 6. 冲突处置

源合同哈希变化、两项已批准决策互斥、任务合同超出批次A、或安全例外被要求直接执行时，立即停止。最小解除条件不是只改次级文件，而是按上节形成新版权威合同、新 SHA、原子引用更新并重新批准。阻塞记录只写可验证事实。

## 7. Git规则

- 每个提交只包含计划内文件；
- 只显式暂存路径，禁止 `git add .` 和 `git add -A`；
- 提交前检查工作区、暂存差异和 `git diff --cached --check`；
- 禁止未经项目负责人明确授权重写既有提交、强制覆盖、配置远程或推送；A1质量审查明确授权的 `git commit --amend --no-edit` 仅用于保持 Commit 1 单提交历史；
- 变更批准记录、验证结果和提交 SHA 必须进入回执。
