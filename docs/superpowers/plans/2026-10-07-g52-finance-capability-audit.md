## 盘点结论

### 当前能力

- Core 费用服务和 `packages/contracts/src/finance.ts` 提供合成只读费用资料：收费项、账单、收据和协议；字段包含金额/币种、账期、版本、绑定版本、来源版本、有效期和状态。`FeeDocumentStatus.PAID` 只是本机预置资料状态，不是支付凭证。API 仅开放 `GET /local/fees`、详情/下载和 `GET /local/fee-summary`；POST 写入测试被拒绝。数据来自进程内预置资料，没有数据库或交易记账。
- User Web 的家长首页通过本地共享客户端请求 `/local/fees`，解析并只投影当前已审核绑定学生的资料；可用资料显示摘要，不可用资料隐藏摘要并说明原因。页面明确只读，不收款、不签署、不连接外部服务。
- Mini `app.json` 注册家长首页而未注册独立 `pages/fees`；共享家长首页已有 Page 级测试读取当前已选学生的共享费用资料。旧的 `pages/fees.ts` 是未注册的固定示例模块，不是当前入口证据。
- Admin `/admin/fees` 已通过共享 `ReviewClient` 请求 `/local/fee-summary`。机构负责人仅获得当前范围汇总和金额合计；平台管理员只获得匿名数量，不显示金额或学生明细。Admin 视图没有付款、退款、签署或账单行写入操作。
- 既有 G2.4 合同与验证记录证明的是本地只读费用资料/摘要的接线；它没有完成 G5.2 账簿、付款流水、退款流水或对账。

### G5.2 缺口与边界

- 当前数据模型把“费用文档”和“账务流水”混为一处：没有独立交易 ID、收支方向、发生时间、关联收费项/账单版本、退款记录或可核对的应收/已记/已退/余额汇总。因此不能称为账簿或对账闭环。
- 路线要求先有合成账本与只读视图；可以新增不可变的固定合成流水样例并按已审核家长关系过滤，但不能新增真实支付/退款动作。每个视图必须标明“合成示例，不代表真实收付款”，状态不能被用户输入改变。
- 保持现有安全边界：API 继续从会话确定租户/校区/班级；家长只读本人当前有效关系；负责人只看当前授权范围的汇总；平台仅匿名统计。禁止在 Admin 增加学生级流水读取。
