# 身份与授权草案

## 1. 统一用户模型

```text
User
├─ 微信身份（未来）
├─ 手机号身份（未来）
├─ 网页登录身份（未来）
└─ 一个或多个机构 Membership
```

`User` 表示同一自然人的平台主体；登录身份只负责证明主体，不能直接授予业务权限。`Membership` 表示 User 与一个 Tenant 的成员关系，并承载状态、角色和数据范围。当前原型均为模拟身份，不接真实微信、短信、手机号或密码。

学生首期不独立注册，不拥有 User、Membership 或授权角色。受监督学生交互由家长或教师从已有学生档案开启。

## 2. 核心概念

| 概念 | 责任 | 关键守卫 |
|---|---|---|
| User | 聚合多个登录身份的稳定主体 | 身份合并须独立验证，不以手机号文本直接合并 |
| Identity | 微信/手机号/网页登录凭据映射 | 凭据环境隔离、可撤销；本批次不实现 |
| Membership | User 与 Tenant 的关系 | 必须有效、不能跨租户复用 |
| Role | 能力集合的命名 | 只在当前 Membership 内生效 |
| Permission | 对资源与动作的最小许可 | 默认拒绝，不能仅靠页面隐藏 |
| DataScope | 校区、班级、学生关系、本人、对象等范围 | 与 Permission 同时满足才放行 |

### 2.1 家长绑定前的受限 OnboardingScope

家长首次绑定时尚无机构 Membership，不能套用成员权限。未来流程先验证平台 `User` 身份，再由服务端校验一次性机构邀请码；服务端解析候选 `tenant_id`、`campus_id` 和学生匹配范围，签发短时、不透明、一次性 `OnboardingScope` token。客户端提供的邀请码、学生姓名或班级只作为匹配输入，不是租户、校区、学生或权限的权威来源。

`OnboardingScope` 只允许提交绑定申请和查询本人申请状态，不允许读取学生档案、机构成员数据或其他申请。错误统一为通用无效/不可继续，避免枚举机构、校区、班级或学生。审核通过时，在同一事务内创建或激活家长 Membership、建立 `GuardianRelationship`、关闭申请并消费该 scope；审核拒绝、撤回或 scope/邀请码过期时不创建 Membership 或关系。

## 3. 七个基线角色

| 角色 | 基本能力 | 数据范围 | 明确禁止 |
|---|---|---|---|
| 访客 | 读取已发布公开内容，提交最小模拟意向 | 指定机构公开投影 | 内部内容、草稿、学生数据、后台 |
| 家长 | 管理本人绑定/请假/接送与 AI 监督 | 当前租户内已通过关系的学生，必要时限校区 | 未关联学生、教师日报、AI 摘要正文、后台 |
| 教师 | 任务、班级必要记录、教师日报、AI 监督与摘要 | 当前租户、授权校区、班级/任务/学生 | 未授权班级、自动纪律/绩效结论、外发摘要 |
| 工作人员 | 内部指南、资源、伙伴云入口与岗位操作 | 当前租户、授权校区、岗位资源 | 默认学生内容、教师日报、发布和角色管理 |
| 机构管理员 | 机构内容、成员、审核、文件与日志 | 单一当前租户及获授权校区；敏感对象另校验 | 其他租户、AI 摘要正文、篡改审计 |
| 校区负责人 | 授权校区的成员、流程、日报和汇总 | 当前租户 + 明确 `campus_id` | 其他校区/租户、AI 摘要正文、自动绩效结论 |
| 平台管理员 | 租户目录、平台配置和运行元数据 | 默认只有平台元数据 | 默认学生/家庭/健康/接送/AI 正文及无审计跨租户访问 |

角色名称与范围必须与 `docs/product/ROLE_MATRIX.md` 一致。学生不是第八个角色。

## 4. 权限判定

```text
验证身份
→ 选择有效 Membership
→ 选择一个当前角色
→ 校验租户状态
→ 注入 tenant_id
→ 校验并注入 campus_id / 班级 / GuardianRelationship / 本人 / 对象范围
→ 校验资源、动作和对象状态
→ 执行或默认拒绝
→ 敏感动作追加审计
```

控制器/API 入口完成认证和基础范围形成，应用服务执行资源/动作/对象状态策略，仓储层强制附加租户/校区范围形成纵深防御。客户端传入的 `tenant_id` 不是授权输入。

### 4.1 RequestScope 版本与指纹

服务端统一 `RequestScope` 至少包含：`user_id`、`membership_id`、当前 `role_id`、`tenant_id`、规范化 `campus_id` 集合、班级集合、学生/GuardianRelationship 范围、权限集合，以及 Membership、角色/权限策略、校区/班级授权、家长关系等相关版本。服务端对规范序列计算不透明 `scope_fingerprint`，同时携带 `scope_version`；两者都不能由客户端提供或覆盖。

任一身份、角色、权限、校区、班级、学生关系、Membership 状态或相关版本改变，都必须形成新指纹并拒绝旧范围。`OnboardingScope` 使用独立受限指纹，审核通过后不能升级复用；必须以新 Membership 重新形成完整 RequestScope。

## 5. 多角色与多机构切换

- 用户必须显式选择一个 Membership 与其中一个角色；页面显示当前机构、校区和角色。
- 切换时重新签发/形成服务端上下文并重新计算权限，不把多个角色合并成超集。
- 切换失败时保留原安全上下文或退出，不沿用目标角色的局部权限。
- 浏览器标签页、缓存和异步任务均绑定上下文版本；Membership 停用后失效。

## 6. 家长与学生关系

家长权限来自已通过且未解除的 `GuardianRelationship`，不来自知道学生姓名、班级或邀请码。绑定必须经历微信登录概念、手机号、邀请码 + 学生姓名 + 班级、服务端受限 OnboardingScope、机构审核、事务性创建/激活家长 Membership 与建立关系的锁定顺序。拒绝、解除或关系失效后立即停止读取学生内容。家长只见 AI 监督开关、会话状态和安全提示，不接收 AI 学习摘要正文。

## 7. 教师班级范围

教师 Membership 关联一个或多个获授权班级/任务范围。读取或写入学生记录、接送、异常、日报汇总和 AI 摘要时，同时校验租户、校区、班级与对象。班级调动或权限撤销后旧缓存和会话失效。工作人员角色不能借同一 User 自动继承教师范围。

## 8. 管理权限

- 机构管理员只能管理当前租户内允许的内容、成员、审核和日志；敏感学生对象仍需单独业务权限。
- 校区负责人所有管理操作均受明确 `campus_id` 限制，不能因机构内角色扩大为全机构。
- 角色分配者不能授予超过自身租户、校区或能力范围的权限。
- 平台管理入口与机构管理网页分离；平台管理员的受控支持例外要求单独批准、最小字段、限时和审计。
- AI 摘要正文仅授权教师可读，机构管理员、校区负责人和平台管理员最多读取不含正文的审计元数据。

## 9. 拒绝、审计与撤销

无 Membership、状态失效、角色不符或范围冲突统一默认拒绝，不泄露对象是否存在。跨租户/校区尝试、角色分配、绑定审核、文件授权、发布、AI 会话开启和受控支持访问写入最小审计。登出、Membership 停用、关系解除、机构开关关闭或高风险事件可撤销会话与授权。

本批次不实现认证协议、密码策略、令牌格式、真实账号恢复或生产管理员流程。
