# 消息投递与回执草案

## 1. 边界

本文定义未来消息通知的事件、接收人、渠道投递、回执、失败重试与人工跟进规则，只作为离线架构草案。当前本地通知/确认仅是合成演示；本文不证明存在消息投递器、微信订阅配置、真实送达或生产权限。

不在业务数据库事务中直接调用外部渠道。业务事件与待投递记录在同一事务内提交，事务成功后才由独立投递器处理。业务对象状态始终以业务记录为准，通知只是提示与回执载体。

## 2. 事件与接收人

每个 `MessageEvent` 使用稳定且不可复用的 `event_id`，引用 `tenant_id`、适用的 `campus_id`、业务对象 ID、业务对象版本、事件类别、发生时间和安全的模板参数版本。租户/校区和触发者由可信服务端上下文生成，不接受客户端传入值。事件记录不得包含密码、令牌、签名链接、模型内部日志或完整学生/健康正文。

接收对象按业务事件逐项解析：教师依据当前有效 Membership、负责班级和职责范围；家长依据当前有效的 `GuardianRelationship`。一个接收人生成一条独立的 `MessageDelivery`，便于单独授权、重试、取消和记录回执。接收人快照只保存完成投递和审计所需的不透明主体引用及范围/关系版本，不复制姓名、手机号或学生档案。

只有业务状态确已提交且该事件类型允许通知时才创建事件。例如，成长记录单独发布后可向有效关系家长提示“有新的成长记录可查看”；请假审核完成后可向申请家长提示“请假申请有新结果”。草稿、未审核材料和敏感异常不会自动通知家长；需关注内容须先由授权人员复核并按批准投影处理。

入队时的接收人集合不能代替发送时授权。投递器发送前必须重验成员状态、关系状态、班级/校区范围、业务对象版本、消息用途和渠道授权。关系、成员或对象版本已变化时，尚未发送的项目转为取消或需要授权角色处理；不能按旧范围继续发送。已经交付到外部渠道的消息不能被系统描述为已撤回。

## 3. 状态分层

业务状态、投递状态、接收回执和人工跟进是不同状态轴。一个轴的状态不能推断另一个轴，例如业务发布成功不代表消息已发送，渠道接受不代表家长已看到，已读也不代表已确认。

### 3.1 投递状态 `DeliveryStatus`

| 状态         | 含义                                                           | 允许的后续状态                                              |
| ------------ | -------------------------------------------------------------- | ----------------------------------------------------------- |
| `QUEUED`     | 事务已提交，等待投递器领取                                     | `SENDING`、`CANCELLED`                                      |
| `SENDING`    | 投递器已领取并正在进行一次渠道调用                             | `SENT`、`RETRY_WAIT`、`FAILED`、`CANCELLED`                 |
| `SENT`       | 渠道已接受该次请求；不代表用户设备收到                         | `DELIVERED`、`RETRY_WAIT`、`FAILED`                         |
| `DELIVERED`  | 收到可验证的渠道送达证据                                       | 保持终态；迟到重复证据仅去重                                |
| `RETRY_WAIT` | 暂时失败，等待有上限的再次尝试                                 | `SENDING`、`FAILED`、`CANCELLED`                            |
| `FAILED`     | 永久拒绝，或有限重试耗尽                                       | 保持终态；经授权人工处理只能创建新尝试/事件，不改写失败历史 |
| `CANCELLED`  | 因撤回、授权失效或版本变更而停止；仅在能确认渠道尚未接受时标记 | 保持终态                                                    |

具体最大重试次数、间隔、超时、渠道回执期限和过期策略待真实供应商/运营规则确认；正式实现必须设置有限上限，不能无限重试。成功响应、进程日志或渠道请求被接受都不能伪造 `DELIVERED`。投递尝试逐次留痕，不覆盖前次结果。

`SENT` 只有在渠道给出明确可重试失败证据，或已确认该渠道幂等机制可安全处理重复请求时，才可进入 `RETRY_WAIT`；单纯缺少送达回执不能自动再次发送，应显示结果待确认并交授权角色核查。渠道已接受但随后证实永久失败时，记录该失败证据并转 `FAILED`。

### 3.2 接收回执 `RecipientReceipt`

回执独立记录 `NONE`、`READ`、`ACKNOWLEDGED`。`READ` 只由当前授权接收人在已登录页面实际打开该条消息后产生；系统通知预览、渠道已送达、列表预加载均不算已读。`ACKNOWLEDGED` 必须由接收人对明确提示的具体业务对象及版本主动确认；不自动触发、不把已读推断为知悉，也不改变原业务对象状态。

回执关联 `event_id`、`delivery_id`、接收人引用、业务对象/版本、当前授权关系版本、动作时间和请求关联 ID。重复回执按同一接收人、事件和对象版本幂等；错误主体、旧关系、旧对象版本或跨租户/校区回执拒绝。撤权后保留既有回执作为历史事实，但不再提供学生内容访问。

允许的回执转换为 `NONE → READ → ACKNOWLEDGED`；已读不能跳过明确确认直接成为知悉，旧事件或旧业务版本的回执不能推进新版本状态。重复相同动作保持原状态并返回既有结果。

### 3.3 人工跟进 `FollowUpStatus`

人工跟进独立记录 `NOT_REQUIRED`、`REQUIRED`、`IN_PROGRESS`、`COMPLETED`。永久失败、超过重试上限或需人工复核的敏感事件转为 `REQUIRED`，并只分派给当前有职责的教师/校区处理角色。跟进人记录采取的联系动作及结果类别，不在日志复制消息正文或敏感学生材料。完成跟进不改写投递/送达/已读状态；超出职责范围的角色不能关闭跟进项。

允许的跟进转换为 `NOT_REQUIRED → REQUIRED → IN_PROGRESS → COMPLETED`；授权处理者可在完成当前步骤时从 `REQUIRED` 直接转为 `COMPLETED`，并留下结果类别。已完成事项不重开或覆盖；后续新问题创建新的跟进事项。

## 4. 渠道、重试与幂等

渠道由服务端按事件用途、接收人授权和机构配置选择；客户端不能指定供应商、接收人地址或模板。微信消息类型、模板/订阅授权流程、备用渠道、费用、服务区域及供应商留存条款均未确定，须在真实接入合同单独确认。

每次发送使用本地稳定的 `delivery_id` 和尝试编号；渠道支持幂等键时使用二者构造请求键。若渠道不支持幂等，系统不能承诺“恰好发送一次”，必须通过回执去重、可追踪的尝试历史和人工核对控制重复风险。渠道回调先验签并校验环境、渠道消息 ID、事件 ID、接收人和对象版本；按渠道事件 ID 去重。伪造、重复、迟到或顺序颠倒的回调不得将状态倒退、跨人关联或覆盖较新的事实。

暂时性限流/超时/依赖不可用可以进入 `RETRY_WAIT`；永久无效授权、禁用渠道、无效接收对象或内容策略拒绝应进入 `FAILED` 或 `CANCELLED`，不可盲目重试。重试耗尽后产生可见人工跟进任务，不静默丢弃。投递器重启后依据已提交的待投递记录恢复，重复领取由并发锁/租约和状态版本防护；具体锁时长和退避参数留待实际容量与供应商条件确认。

## 5. 内容、隐私与租户边界

通知正文只含让接收人知道“有一项可查看事项”的最小提示，并引导在重新授权的应用内查看。例如成长记录发布后可提示“有新的成长记录可查看”，不得在锁屏消息中放学生姓名、健康/异常详情、教师待复核内容、其他学生信息、模型内部日志或未经人工复核的敏感判断。

家长消息仅面向其当前有效关系对应的学生，内容范围仍服从 A2 四字段已批准投影；教师通知只面向负责班级的当前教师；机构与校区角色依职责范围处理。任何后台任务、缓存键、投递记录、渠道回调、跟进任务和审计查询都绑定可信 `tenant_id` 与适用校区/班级/关系范围。不可用或范围不确定时拒绝发送/读取，不切换到其他租户数据或过期缓存。

## 6. 审计与故障展示

最小审计事件包括事件创建、接收人解析、授权重验、尝试开始/结果、渠道回执、重试安排/取消、状态终结、人工跟进分派/完成、读取和主动知悉。只记录执行主体/渠道、可信范围、对象/事件/版本引用、状态前后值、尝试编号、结果类别、时间与关联 ID；不记密钥、令牌、签名 URL、接收人联系方式或消息/学生敏感正文。访问投递记录和回执本身也按接收人和职责范围授权。

界面必须分别呈现“业务已发布”“通知待处理/渠道已接受/已送达/发送失败”“接收人已读/已确认”和“需人工跟进”。渠道不返回送达回执时显示“发送结果待确认”，不能把 `SENT` 改写成“已送达”。系统不可用时保留可恢复失败状态或明确提示人工跟进，不显示成功，不影响业务对象的真实状态。

## 7. 未来验收与待定事项

未来真实实现至少验证：事务提交失败时无待投递项；事件重复消费不会重复创建业务对象；错租户/校区/班级/关系拒绝；撤权或版本变化会取消待发项；渠道接受不能生成已读/知悉；只有验签回执能产生送达证据；收件人主动打开与确认分别产生 READ/ACKNOWLEDGED；重复、迟到、倒序和伪造回执安全去重/拒绝；临时故障有界重试、永久故障不重试、耗尽后创建人工跟进；重启可恢复待投递项；消息正文与审计不泄露敏感材料；处理角色无法越界查看或关闭跟进。

以下事项未由本草案决定：具体微信渠道与消息类别、订阅/模板授权文案、供应商与费用、最大重试次数/间隔、服务等级、渠道回执期限、保存/删除期限、真实运营人工跟进时限。取得必要授权和真实条件前，不接入渠道、不发送消息、不以合成回执宣称实际送达。
